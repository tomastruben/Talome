# Product and Source Research

Research exists to make the app specific to its use case, not to collect fashionable references.

## What to inspect

1. existing Talome screens, native AppSpec components, and nearby project patterns
2. supplied repositories and local source snapshots
3. relevant public GitHub repositories and official library documentation
4. product screen patterns that solve the same user job
5. available shadcn-compatible registries and approved premium component sources

## Evidence standard

For every external candidate record:

- exact repository or official documentation URL
- project/library name and the problem it solves here
- license and whether reuse is permitted
- maintenance evidence such as a recent release or commit date
- compatibility with Talome's stack, self-hosting model, and security constraints
- decision: reuse, adapt, visual inspiration only, or reject
- exact part worth reusing; popularity alone is not a reason

Prefer primary sources. Stars are only a weak signal. Never claim a repository, license, API, or maintenance state without checking it. If network access is unavailable, inspect local sources and record the unresolved lookup instead of fabricating findings.

## Screen-pattern research

Research the workflow anatomy, not only styling. Identify how strong products handle:

- first-use and empty states
- primary creation or decision flow
- information hierarchy and progressive disclosure
- visualization choice and data density
- detail/edit states and recovery from errors
- desktop window, narrow window, and mobile/compact behavior

Translate useful observations into Talome's visual language. Do not clone another product's brand or import a competing design system.
